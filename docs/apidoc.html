REST API for an online bookstore.

This API provides authentication, user management, book management, cart, favourites, orders, and other bookstore-related functionality.

auth

Authentication and account verification endpoints.

Includes:

  • User registration
  • User login
  • Email OTP verification
  • Resending OTP
  • Forgot password
  • Reset password

Register a new user

Creates a new user account using the provided personal information.

After successful registration, an OTP is generated and sent to the user's email address. The user must verify this OTP using the /auth/verifyOtp endpoint before the email address is considered verified.

This endpoint is publicly accessible and does not require authentication.

Registration flow

  1. Client submits the user's registration information.
  2. Server validates the registration data.
  3. A new user account is created.
  4. An OTP is generated and sent to the provided email address.
  5. The client uses /auth/verifyOtp to verify the email address.

Log in to an account

Authenticates an existing user using their email address and password.

If the credentials are valid, the server returns a JWT access token. The returned token can be supplied in the Authorization header when accessing protected API endpoints.

Authentication flow

  1. User submits their email address and password.
  2. Server validates the credentials.
  3. If valid, a JWT token is generated.
  4. The client stores the JWT token.
  5. The client sends the token with protected API requests.

Authorization header

Protected requests should include:

Authorization: Bearer <JWT_TOKEN>

This endpoint is publicly accessible and does not require an existing authentication token.

Verify email OTP

Verifies the one-time password (OTP) that was sent to the user's email address during registration.

When the OTP is valid, the user's email address is marked as verified and a JWT access token is returned.

Verification flow

  1. User registers using /auth/register.
  2. Server sends an OTP to the registered email address.
  3. User submits the OTP and email address to this endpoint.
  4. Server validates the OTP.
  5. The user's email is marked as verified.
  6. A JWT access token is returned.

This endpoint is publicly accessible and does not require authentication.

Request Body schema: application/json
required

Email address and OTP received by the user.

otp
required
integer [ 100000 .. 999999 ]

Six-digit OTP sent to the user's email.

email
required
string <email>

Request password reset email

Requests a password reset email for a user account.

The current implementation requires a valid JWT bearer token. The email address is supplied in the request body and is used to identify the account for which the password reset process is started.

The authenticated user must also have a verified email address.

Authentication

This endpoint requires:

Authorization: Bearer <JWT_TOKEN>

Password reset flow

  1. Client authenticates using a JWT.
  2. Client submits the account email address.
  3. Server validates the JWT.
  4. Server checks whether the user's email is verified.
  5. Server sends a password reset email.
  6. The email contains a password reset token.
  7. The client uses the reset token with /auth/resetpassword/{token}.
Authorizations:
bearerAuth

Reset user password

Changes the authenticated user's password using a password reset token.

The reset token is supplied as a path parameter and is expected to have been provided to the user through the password reset email.

The current implementation also requires a valid JWT bearer token.

Authentication

This endpoint requires:

Authorization: Bearer <JWT_TOKEN>

Reset password flow

  1. User requests a password reset.
  2. Server sends a reset email containing a reset token.
  3. Client extracts the reset token from the reset link.
  4. Client sends the reset token in the URL.
  5. Client sends the new password in the request body.
  6. Server validates the JWT and reset token.
  7. User's password is changed.
Authorizations:
bearerAuth
path Parameters
token
required
string
Example: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.reset-token

Password reset token sent to the user's email address.

This token identifies and authorizes the password reset operation.

Request Body schema: application/json
required

The new password that should replace the user's existing password.

New password that replaces the existing password.

Get sales and revenue analytics

Retrieves aggregated sales metrics for non-cancelled orders grouped by day, week, or month.

Optional query parameters allow filtering by date range (startDate and endDate) and selecting the aggregation period (groupBy):

  • day: Groups data daily (YYYY-MM-DD) [default]
  • week: Groups data weekly (YYYY-Www)
  • month: Groups data monthly (YYYY-MM)

For each time bucket, the response returns:

  • totalRevenue: Sum of total prices
  • avgRevenue: Average order value
  • totalOrders: Count of orders
  • totalItems: Total quantity of books purchased

Rate limit: 30 requests per minute.

Authorizations:
bearerAuth

startDate
string <date>
Example: startDate=2026-01-01

Earliest order creation date to include (inclusive).

endDate
string <date>

Latest order creation date to include (inclusive).

groupBy
string
Default: "day"
Enum: "day" "week" "month"
Example: groupBy=day

Time-series bucket granularity.

Add a book to the shopping cart or increment quantity

Adds a specified quantity of a book to the authenticated customer's shopping cart.

If a cart does not yet exist for the user, a new one is initialized. If the item is already in the cart, its quantity is increased and financial totals are recalculated. Synchronizes changes with Redis caching.

This endpoint requires authentication and is restricted to customers with role: 'user'.

In-Depth Business & Controller Logic

  1. Input Extraction:
    • Extracts bookId and quantity from request body.
    • Extracts userId from authenticated req.user.id.
  2. Inventory Stock Pre-Check:
    • Queries Books.findById(bookId).
    • Verifies that book.stock >= quantity. If the requested quantity exceeds total book stock, rejects immediately with HTTP 400 Bad Request: "No book stock is available yet, please contact admin to futher information".
  3. Cart Discovery & Evaluation:
    • Queries MongoDB for an existing cart via Cart.findOne({ user: userId }).
  4. Branch A: Cart Does Not Exist:
    • Initializes a new Cart document:
      {
  "user": "userId",
  "items": [{ "book": "bookId", "quantity": quantity }],
  "totalQuantity": quantity,
  "totalPrice": book.price * quantity
}
  5. Branch B: Cart Already Exists:
    • Searches for bookId within cart.items:
      • Case 1: Book already exists in cart (index > -1):
        • Calculates newTotalQty = existingQty + quantity.
        • Stock Validation: If newTotalQty > book.stock, rejects with HTTP 400 Bad Request: "Only <availableStock> more units available".

Automatically recalculates cumulative price (totalPrice) and quantity (totalQuantity) based on the removed book's unit price, and synchronizes the updated cart with Redis cache.

  1. Parameter & ObjectId Validation:

  2. Cart Discovery:
    • Looks up the user's cart in MongoDB: Cart.findOne({ user: id }).

Delete the authenticated customer's review for a book

Permanently deletes the customer's review and star rating for the specified book.

Authentication & Access Control

  • Required Authentication: Bearer JWT token (protect middleware).
  • Role Restriction: Accessible only to customers holding role: 'user' (restrictTo("user")).
  • Email Verification: User account email address must be verified (isEmailVerified: true).

Operational Logic

  1. Executes Review.findOneAndDelete({ book: bookId, user: req.user.id }).
  2. Automated Rating Resynchronization: A Mongoose post(/^findOneAnd/) middleware hook executes immediately after deletion:
    • Recalculates the book's remaining review statistics via calcAvgRating(doc.book._id).
    • Updates ratingQuantity and ratingAverage on the Books document.
    • If all reviews for the book have been deleted, automatically resets both ratingAverage and ratingQuantity to 0.

Rate Limiting

  • Protected by generalRateLimiter: Maximum 15 requests per minute per client IP.

Retrieve all catalog reviews across all books (Admin only)

Provides comprehensive administrative oversight of all customer reviews submitted across the bookstore catalog.

Authentication & Access Control

  • Required Authentication: Bearer JWT token (protect middleware).
  • Role Restriction: Strictly restricted to users holding role: 'admin' (restrictTo("admin")).
  • Email Verification: Admin account email address must be verified (isEmailVerified: true).

Search & Filtering Capabilities

  • Keyword Search (msg): Optional case-insensitive regular expression substring filter ({ review: { $regex: msg, $options: "i" } }) searched across all review bodies in the database.
  • Catalog-wide Scope: Unlike the book-specific review endpoint, this queries all reviews without filtering by a specific book ID.

Sorting Behavior

  • sort=new (default): Sorts descending by -createdAt (most recently submitted reviews first).
  • sort=old: Sorts ascending by createdAt (oldest reviews first).
  • Any unrecognized or omitted sort option automatically defaults to new.

Pagination Rules

  • page: 1-based page index (defaults to 1).
  • limit: Number of records returned per page (defaults to 10).
  • Upper Bound: If limit exceeds 100, the server automatically caps it at 100.
  • Computes skip = (page - 1) * limit.
  • Computes totalPages = Math.ceil(totalItems / limit) and hasNextPage = page < totalPages.

Data Population

  • Automatically populates the author's public name (user: { _id, name }) and book title (book: { _id, title }) via Mongoose pre(/^find/) query middleware.

Rate Limiting

  • Protected by getRateLimiter: Maximum 30 requests per minute per client IP.

Retrieve current user's review for a book (with Redis caching)

Retrieves the specific review and rating written by the authenticated customer for the designated book, utilizing a high-performance Redis cache-aside caching pattern.

Authentication & Access Control

  • Required Authentication: Bearer JWT token (protect middleware).
  • Role Restriction: Accessible only to customers holding role: 'user' (restrictTo("user")).
  • Email Verification: User account email address must be verified (isEmailVerified: true).
  • Parameter Validation: Middleware validateId("bookId") validates that bookId is a valid 24-character hexadecimal MongoDB ObjectId before controller execution.

High-Performance Redis Cache-Aside Architecture

  1. Cache Lookup: Checks Redis for key user:{userId}:book:{bookId} using client.get(...).
  2. Cache Hit:
    • Returns cached serialized review immediately from Redis memory without querying MongoDB.
    • Responds with HTTP 200 OK: { status: "success", message: "review found successfully", data: JSON.parse(reviewData) }.
  3. Cache Miss:
    • Queries MongoDB for an existing review via Review.findOne({ book: bookId, user: req.user.id }).
    • If no review exists, aborts with HTTP 404 Not Found ("Review not found").
    • If found:
      • Serializes the review document and writes it to Redis key user:{userId}:book:{bookId}.
      • Responds with HTTP 200 OK: { status: "success", data: review }.

Rate Limiting

  • Protected by getRateLimiter: Maximum 30 requests per minute per client IP.
